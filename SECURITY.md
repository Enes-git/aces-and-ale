## Security Posture

This document owns the threat model, security requirements, controls, and trust-boundary enforcement. [REQUIREMENTS.md](REQUIREMENTS.md) owns nonsecurity behavior, actors, workflows, business records and integration scope. This document also owns security-related privacy/regulatory constraints and disclosure policy. [DESIGN.md](DESIGN.md) owns frontend interaction and accessibility. [ARCHITECTURE.md](ARCHITECTURE.md) owns components, interfaces, data flows, and dependency direction.

No implementation is assumed. Controls below describe required or proposed future behavior, not evidence that controls exist or have passed testing. Rules authored here are the repository security posture. Explicit ASSUMPTION/proposed clauses retain proposal status; relocating them does not approve them. Unmarked control imperatives remain required. New review safeguards explicitly labeled required below close gaps for the resolved scope; their mechanisms remain undecided. `UNKNOWN` marks missing facts; `TO BE DECIDED` marks unresolved decisions; `ASSUMPTION` marks project-specific proposals or inferred threats. Rule identifiers beginning `SEC-` and threat identifiers beginning `TH-` are local to this document, not standards identifiers.

- **Confirmed authentication policy:** Passkey only for everyone. Encourage users to set up two devices during registration. Source: the human Security Notes supplied with this task.
- **Architecture and exposure:** Components, technologies, provisional allocations and external interfaces are owned by [ARCHITECTURE.md](ARCHITECTURE.md). Deployed origins/domains, hosting, API protocol, identity services and operational access paths: TO BE DECIDED.
- **Authorization and disclosure:** The human public-tournament/admin decisions and delegated launch decisions are recorded in the policy below. Authentication does not itself grant permission.
- **Privacy:** Jurisdictions, legal obligations, retention/deletion and classifications beyond the bounded disclosure policy: TO BE DECIDED. No payment, age-verification, health-data or other regulatory obligation is inferred.
- **Reference applicability:** The supplied Node.js 26, React 19, and React Native 0.87 prompts were supplied as authoritative security defaults for applicable capabilities. The authored controls below record the repository baseline; mutable external files are not an implicit policy update. Future source changes require applicability review and reconciliation here, preserving the supplied baseline rather than silently weakening it. Their version labels do not select Node.js 26 or React Native 0.87 for deployment. Language, framework, library, session, provider, and tooling choices remain TO BE DECIDED where the architecture leaves them open.

## Access and Disclosure Policy

**SEC-ACCESS-02 — Required disclosure/grant matrix.** Source: human decisions of 2026-10-13 for tournaments and the four requested administrative action groups; commerce/internal-data and start-operation grants below are minimal launch decisions under the user's delegated scope. An admin means an account with a trusted server-established grant, not a client actor label. Other actor categories do not confer additional permissions.

| Surface / operation | Grant and disclosure |
| --- | --- |
| Tournament read, including a newly created empty/incomplete draft | Anonymous and authenticated read from creation. Deliberate public projection: tournament reference/state, assigned participant display names and match references/competitors, plan, scores/results and derived tournament statistics under FR-1–FR-5. Additional tournament fields require explicit classification before exposure. |
| Create tournament, assign participants, enter/change plan, enter/correct scores/results | Authenticated admin only. |
| Start play | Authenticated admin only; business preconditions remain in FR-1.1. |
| Catalog/menu and stock administration, stock adjustments, merchandise sales, order creation/completion/cancellation, commerce reads/totals/history | Authenticated admin only for launch. No public commerce catalog/menu or extra staff role is introduced. |
| World/local ranking reads | Anonymous/authenticated reading of the deliberate ranking representation in FR-4.1/4.2; underlying source records are not implicitly public. |
| Account/credential/session records, account-player links, privileges, audits/diagnostics and operational metadata | Excluded from public representations. Only explicitly authorized identity/operational handling may access them; admin status alone is not a blanket diagnostic/secret-access grant. Detailed grants: TO BE DECIDED. |
| Unspecified operations (including registration eligibility/admin provisioning) | No implied grant; explicit policy required before enabling them. |

Responses MUST project deliberately allowed fields rather than serialize whole domain/persistence objects. Tournament publicity does not publish account associations or commerce records. Public identifiers are references, not secrets or access tokens. Unauthorized protected requests MUST have no protected state change or sensitive side effect and MUST not disclose protected fields or distinguish inaccessible from nonexistent protected objects unnecessarily. Exact protocol response forms: TO BE DECIDED.

**Acceptance criteria:** Anonymous read of a zero-player draft returns its public fields without identity/commerce/diagnostic fields. Admin requests satisfying functional preconditions succeed for each granted operation; anonymous and authenticated nonadmin requests fail without change, including direct requests, substituted object references and privilege fields. Public ranking responses expose only their defined representation. Internal commerce reads fail for anonymous/nonadmin requesters. Field-substitution attempts cannot add ungranted fields or reveal internal records.

## Threat Model

**ASSUMPTION:** Consider unauthenticated requesters, authenticated users exceeding their eventual permissions, malicious browser content, modified mobile clients, network attackers, and compromised dependencies or operational credentials. These are threat scenarios, not allegations about the listed actors. Deployment exposure, likelihood, impact ratings, and accepted residual risk are TO BE DECIDED.

**ASSUMPTION:** Protect the integrity and permitted disclosure of the application-owned tournament, participant, match, plan, score, statistics, and ranking data. Passkey account associations, credential records, session material, configuration secrets, and security logs are additional security assets whose schema and storage are TO BE DECIDED. Commerce catalog/menu, stock, order/sale history, price snapshots and totals defined in [REQUIREMENTS.md](REQUIREMENTS.md) are additional integrity assets; commerce records are internal under SEC-ACCESS-02.

Every threat below is an **ASSUMPTION** derived from the documented surfaces and proposed boundaries.

| ID | Abuse scenario and affected asset | Enforcement point and relevant controls |
| --- | --- | --- |
| TH-01 | A requester attaches a passkey to another account, replays a ceremony, or exploits recovery to take over an identity. | Application identity handling; SEC-AUTH-01 through SEC-AUTH-04. |
| TH-02 | A client changes an object reference or claimed actor category to read or modify another user's permitted records. | Application authorization on each protected operation/object; SEC-ACCESS-01. |

## Security Requirements

**SEC-AUTH-01 — Passkey-only authentication.** All user authentication MUST use passkeys, including authentication by any actor category later granted administrative permissions. Password, email/SMS code, magic-link, or other non-passkey sign-in fallbacks MUST NOT be introduced. This policy does not determine which views require sign-in. Service-to-service and operational identities are UNKNOWN; their policy is TO BE DECIDED. Source: human Security Notes.

**SEC-AUTH-02 — Registration encouragement.** Registration MUST encourage setting up access on two devices. The second device is encouraged, not a mandatory registration gate. Exact interaction, supported devices, and enrollment tracking are TO BE DECIDED. A synced passkey can be available on several devices, so credential count cannot be treated as proof of two independent recovery methods. Source: human Security Notes and [FIDO passkey synchronization guidance](https://fidoalliance.org/passkeys/).

**SEC-AUTH-03 — ASSUMPTION: proposed passkey verification.** Use a maintained WebAuthn-compatible verifier in the application; library and native integration are TO BE DECIDED. Bind cryptographically random, expiring, single-use challenges to the ceremony and intended account context. Verify ceremony type, challenge, expected origin, RP ID, account/credential association, required presence/verification flags, algorithms, registration response, and assertion signatures before accepting authentication. Prevent reuse and cross-account credential attachment. **ASSUMPTION:** Require user verification for passwordless ceremonies; policy confirmation is TO BE DECIDED. RP ID, origin allowlist, attestation policy, challenge limits, expiry, and authenticator compatibility are TO BE DECIDED. This is a project proposal derived from [WebAuthn Level 2, registration](https://www.w3.org/TR/2021/REC-webauthn-2-20210408/#sctn-registering-a-new-credential) and [assertion verification](https://www.w3.org/TR/2021/REC-webauthn-2-20210408/#sctn-verifying-assertion), not a custom cryptographic protocol.

**SEC-AUTH-04 — ASSUMPTION: credential lifecycle and recovery.** Require recent successful passkey verification before adding or removing a credential on an existing account; protect these operations against request forgery and account substitution. Freshness, initial registration/bootstrap, revocation, last-credential removal, and all-devices-lost recovery are TO BE DECIDED. Recovery must be reconciled with SEC-AUTH-01 before implementation; no weaker fallback or support override is implicitly authorized. Authentication records must not equate player names with unique account identities.

**SEC-ACCESS-01 — Server authority.** The API MUST independently authorize each protected operation and object using trusted server context. Client roles, hidden controls, route state, object references, and native assertions grant no authority. Reject unvalidated privilege/ownership fields rather than binding request bodies directly to records. Deny protected operations lacking an explicitly defined grant under SEC-ACCESS-02. Exact protocol rejection form remains TO BE DECIDED; the no-change/no-disclosure outcome is required. Sources: S-JS, S-REACT, S-NATIVE.

**SEC-INPUT-01 — Runtime validation.** Validate incoming commands, API responses at clients, stored client values, and configuration at their receiving boundary. Use allowlisted security-sensitive fields and bound types, bytes, structure, collections, and computational cost. Reject prototype-polluting keys; keep untrusted data out of dynamic execution and module selection. Type annotations cannot substitute for runtime checks. Apply checks to stored/read-back text, names, catalog/menu text, quantities, currencies, monetary precision, object references and lifecycle commands. Reject nonfinite/out-of-range monetary values, unsupported fields and malformed collections. Server-derived snapshots/totals cannot be mass-assigned; authorized catalog/menu price edits and explicit valid completion commands remain supported. Exact schemas and limits are TO BE DECIDED against resolved FRs; do not invent player-name, tennis-score or ranking rules. Sources: S-JS, S-NODE, S-REACT, S-NATIVE; S-TS only if TypeScript is selected.

**SEC-DATA-01 — Data integrity and persistence.** Bind SQL values and allowlist dynamic query structure. The application MUST enforce resolved business rules independently of the originating client, coordinating database consistency where needed. Enforce the FR-1.1 start precondition against hostile and concurrent requests; this does not impose a draft maximum or post-start substitution rule. No duplicate-name restriction, match format, ranking formula, or scoring algorithm is inferred. **ASSUMPTION:** Use a least-privilege application database identity, with schema-changing and operational privileges separated from routine record access. Schema, constraints, transaction/concurrency mechanism, and grants are TO BE DECIDED. Sources: `ARCHITECTURE.md`, S-JS, S-NATIVE.

**SEC-DATA-02 — Required launch integrity.** Independently derive sale/order snapshots, totals and statistics from validated authoritative records under FR-5–FR-8. Preserve those invariants under concurrency, replay and interruption; admitted operations leave a complete permitted state or no business change. Stable operation references bind to the action and content so conflicting reuse is rejected. Do not accept client-supplied computed totals or historical snapshot replacements as authority. Authorized edits to catalog/menu prices and valid explicit state-transition commands are permitted inputs, subject to SEC-ACCESS-02 and FRs. No payment credentials/tokens/authorization codes are accepted or stored in these launch workflows. Transaction/locking/replay/recovery mechanisms: TO BE DECIDED in architecture.

**Acceptance criteria:** Concurrent sales exceeding stock cannot both succeed; stock stays nonnegative. Replaying a sale or completion cannot repeat its effects. Conflicting reference reuse is rejected. Price edits leave historical snapshots intact. Tampered snapshots/totals or invalid transitions do not change records. Corrections update statistics once. Interrupted operations recover consistently across stock/sale and order/sale relationships. Uncertain outcomes follow FR-8.1 without duplicate effects; currency separation follows FR-6.3/7.4.

**SEC-SESSION-01 — Session protection.** Required outcomes: sessions are server-verifiable, bounded in lifetime and revocable; invalidate affected sessions on logout/account disablement, rotate session identity after authentication or privilege elevation, and evaluate current server-side grants on every protected action. Effective admin removal prevents the next admin action. Scope of session invalidation on credential revocation, expiry/freshness values, format, storage and mechanisms are TO BE DECIDED; revoked credentials cannot perform new authentication. Prevent stale client responses/caches from restoring an earlier identity or privilege context; identity-scoped caches must not leak internal representations through public cache entries. If browser cookies carry authentication, use `Secure`, `HttpOnly`, an appropriate `SameSite` policy, and server-side request-forgery protection; cookie attributes alone are insufficient. If native bearer/refresh credentials are selected, protect them using platform credential storage and support bounded lifetime and server-side invalidation. Do not select JWT, a token provider, or browser storage merely because a reference discusses it. Sources: S-JS, S-REACT, S-NATIVE.

**SEC-TRANSPORT-01 — Network authenticity.** Protect remote credential and application traffic with authenticated encryption and certificate/hostname verification. For web/mobile HTTPS traffic, keep verification enabled; release mobile builds must reject broad cleartext and development trust exceptions. If cross-origin browser access is needed, allowlist exact origins; CORS is not API authorization and is not a native-client security boundary. TLS termination, trust configuration, network topology, native app associations, and any pinning decision are TO BE DECIDED. Sources: S-NODE, S-NATIVE.

**SEC-WEB-01 — Safe React rendering.** Render player names and other untrusted values as inert text. Keep untrusted values out of raw HTML, SVG, scripts, styles, arbitrary props, and executable resource URLs. Rich HTML is not required; if later introduced, review its sanitizer and sinks. Apply a restrictive CSP and Trusted Types where supported, with compatibility testing for the selected React minor and rendering strategy; exact policy is TO BE DECIDED. Keep secrets out of client bundles and hydration data. If SSR, Server Components, or Server Functions are selected, separately review request isolation, caching, endpoint authorization, serialization, and request-forgery protection. Sources: S-JS, S-REACT.

**SEC-MOBILE-01 — Native client containment.** Treat the application bundle, local state, device, and native-module outputs as untrusted. Keep credentials out of AsyncStorage and ordinary plaintext files; use iOS Keychain or Android Keystore-backed protection for any application-held session credentials. Platform passkey private keys are not application-managed session tokens. Minimize cached personal data and clear user-scoped state on identity changes and revocation. Request only capabilities required by resolved workflows. Deep links, WebViews, push, and additional device permissions are not established capabilities; if introduced, review destination validation, message provenance, native bridges, and authorization first. Storage libraries and backup policy are TO BE DECIDED. Source: S-NATIVE.

**SEC-RUNTIME-01 — Node.js resource and execution limits.** Bound request parsing, body sizes, timeouts, concurrency, retries, database work and authentication attempts with separately configurable budgets for public reads, ceremonies and authenticated mutations; values are TO BE DECIDED. Include text/participant/order-line collection limits and statistics work. Enforce limits before expensive work where feasible, with no partial protected changes on rejection; retries must not amplify requests or duplicate effects. Numerical budgets require capacity evidence, not invented thresholds. Abuse observations use sanitized events; no CAPTCHA, vendor or account-lockout policy is selected. Use strict protocol parsing when HTTP is selected and trust forwarded identity headers only from explicitly configured intermediaries. Fail startup on invalid security configuration. Keep secrets out of arguments and untrusted data out of shells or dynamic code. Restrict runtime privileges and diagnostics; Node.js permission controls, if applicable to the selected runtime, provide defense in depth and do not sandbox malicious code. Container, reverse-proxy, and runtime-specific mechanisms remain TO BE DECIDED. Sources: S-JS, S-NODE.

**SEC-OPS-01 — Secrets, errors, and accountability.** Exclude credentials, session material, sensitive request/response bodies, and unnecessary personal data from logs, URLs, analytics, crash reports, and client errors. Return safe errors while preserving accessible field feedback required by `DESIGN.md`. Restrict diagnostic artifacts and secret access; mechanisms are TO BE DECIDED. Required scope-resolved accountability: record sanitized authentication/credential events, permission denials and supported administrative mutations (including privilege changes if implemented, tournament/participant/plan/result changes, catalog/menu/stock/sale/order operations). Include action, actor reference where known, target, time, correlation/operation reference, outcome and sufficient changed-field/reason information to investigate integrity changes without copying sensitive bodies. Restrict audit access; public tournament status grants none. Failed accountability recording must be observable and follow a defined fail-or-durable-recovery policy before enabling mutations; coupling mechanism, retention, alerts, incident ownership and response procedures are TO BE DECIDED. This makes the earlier proposed event logging requirement explicit for the resolved admin surface. Sources: S-JS, S-NODE, S-REACT, S-NATIVE.

**SEC-SUPPLY-01 — Dependencies and releases.** Use reviewed, locked dependency resolution and a reproducible build; assess packages, runtime, native modules, and shipped artifacts for applicable advisories. Review lifecycle scripts before execution, keep development/debug surfaces out of releases, and protect native signing credentials. Applicable high/critical dependency findings must be resolved before promotion under the supplied baseline. Reviewed manifest/lock mismatch must fail rather than silently rewrite resolution. Evidence must identify runtime, direct/transitive packages, native modules, lock state, advisory assessment and produced artifact, with reviewed lifecycle scripts and protected signing provenance. Package manager, scanners, release gates, CI/CD system, update tooling and exception authority are TO BE DECIDED. Source version labels and historical review dates are not evidence that a future deployment is patched. Sources: S-JS, S-NODE, S-REACT, S-NATIVE.

## Open Security Questions

1. **Identity and authorization — TO BE DECIDED:** Who may register; how is the first admin established and who grants/revokes privileges; what is the account/player relationship; can one person belong to multiple actor categories? Actor labels alone confer no grant. SEC-ACCESS-02 resolves public reads and launch admin actions; finer operational/account-record grants remain open.
2. **Reference applicability — TO BE DECIDED where conditional:** Node guidance discusses SQLite/deployment examples; the architecture selects its own database and leaves hosting open. React optional SSR/Server Functions and native OAuth/tokens/WebViews do not mandate those capabilities. Password-storage guidance is inapplicable; conditional TypeScript guidance does not select a language or establish toolchain compatibility. Preserve this distinction when reviewing sources.
3. **Passkey configuration — TO BE DECIDED:** RP ID, origins, native associations, authenticators/platforms, user-verification/attestation policy, challenge expiry/limits, verifier and credential schema. SEC-AUTH-03's user-verification and library/verification proposal requires adoption review; no custom crypto protocol is authorized.
4. **Enrollment/recovery — TO BE DECIDED:** Initial bootstrap, credential addition/removal/revocation mechanisms, freshness, last-credential safeguards, all-devices-lost recovery, supported/unsupported-device experience and what counts as two-device setup. Encouragement remains optional; synced credentials do not prove independent recovery methods. Required authority and security outcomes apply to whichever process is selected; no fallback/support bypass is implied.
